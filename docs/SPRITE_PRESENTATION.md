## 0. Scope, and a correction kept visible on purpose

An earlier design conversation (2026-08-03) wrongly assumed the game's creature sprites were modern
placeholder art, and suggested a palette-quantize shader to make them "read as in-world." **That premise was
wrong**, and it's corrected here rather than silently dropped — this repo's standing practice when a wrong
claim makes it into a doc (see `GENERATION_PROFILE.md` §5(a), §6 for the same treatment elsewhere).

**The game already imports and renders genuine Gen 1 sprite art**, and both the source and the current
implementation are working as intended. Nothing in this doc proposes replacing the art. Everything below is
(a) writing down exactly how that pipeline works today — nothing had before — and (b) what Phaser can
additionally *do* to that real art (motion, transient FX, transitions), not what to replace it with.

## 1. Current status — the sprite/cry pipeline, source of truth

### 1.1 Data source — static files fetched at import time, not a DB field

Creature sprites are **not** stored in any database — they're downloaded once, at import time, and served
as static files by convention:

- `PokeApiConnector/SpriteDownloader.cs` fetches front/back PNGs for species IDs 1–151 directly from
  `raw.githubusercontent.com/PokeAPI/sprites/master/sprites/pokemon/{id}.png` (front) and `.../back/{id}.png`
  (back) — GitHub's sprite mirror, not `pokeapi.co` proper.
- They're written to `creaturegame.Web/wwwroot/sprites/{front,back}/{id}.png`, keyed purely by numeric
  species ID. No URL, filename, or sprite reference is persisted anywhere in `pokemon.db`.
- `creaturegame/DB/PokemonSpecies.cs` has **no sprite field at all** — stats, types, catch rate, dex entry,
  nothing sprite-related. Contrast: `Items/Item.cs` **does** carry a `SpriteUrl` column, populated at import
  and read back by `PokeApiConnector/ItemSpriteDownloader.cs` for item icons. Items and creatures use two
  genuinely different patterns — worth knowing if either is ever touched, so a fix to one doesn't get
  assumed to cover the other (see §2).
- Cries follow the identical no-DB-field, ID-keyed convention: `PokeApiConnector/CryDownloader.cs` pulls
  **Gen-1-authentic 8-bit "legacy" cries** from `raw.githubusercontent.com/PokeAPI/cries/main/cries/pokemon/legacy/{id}.ogg`
  into `wwwroot/audio/cries/{id}.ogg`.
- `docs/DATA_IMPORT.md` already documents this at the import-pipeline level: "downloads sprite/cry assets
  into the web app's `wwwroot`... the frontend's Phaser canvas serves these as static files (front for the
  enemy, back for the player); cries fall back to a Web Audio synth if an OGG is missing."
- **Assets are gitignored, not vendored into the repo.** `.gitignore` excludes `wwwroot/sprites/` and
  `wwwroot/audio/` as "runtime-generated by PokeApiConnector; not source files." Whatever's on disk in any
  given checkout is a leftover from a local importer run, not a tracked file.
- **Production/CI gets them via a dedicated Docker build stage**: `Dockerfile` runs a separate `assets`
  stage (`dotnet run --project PokeApiConnector -- assets`) to fetch sprites/cries fresh into every image
  build — the comment there references a past "sprites and cries missing on live" incident, i.e. this stage
  exists because a clean checkout never has the assets on disk by itself.

### 1.2 Wire/API layer — no sprite URL ever crosses the wire

Only the species integer ID does; every consumer reconstructs the path itself:

- `SpeciesController`'s `SpeciesSummaryDto` (the dex/starter-picker payload) and the client's `Species.ts`
  interface both carry stats/types/id — no sprite field on either side.
- Every consumer — `BattleScreen.tsx`, `PartyStrip.tsx`, `CreatureOverview.tsx`, `StarterSelection.tsx`,
  `BattleEndedOverlay.tsx`, `AcquisitionModal.tsx`, `EvolutionPromptModal.tsx`, `PartyCard.tsx`,
  `RecoveryModal.tsx`, and Phaser's own loader in `BattleScene.ts` — builds `/sprites/{front|back}/{id}.png`
  itself, by the same convention, independently, at each call site.
- No shiny/variant concept exists anywhere in the code; front vs. back are the only two sprite variants.

### 1.3 Client rendering — `BattleCanvas.tsx` / `BattleScene.ts`

**Mount** (`BattleCanvas.tsx`): a React effect lazy-imports `phaser` + `BattleScene`, creates a
480×320 `Phaser.Game` (`transparent: true`, `Scale.RESIZE`), and starts the scene with
`{ playerSpeciesId, enemySpeciesId }` as init data. Species IDs are fixed for the mount's lifetime; the
whole `Phaser.Game` is destroyed on unmount.

**Loading**: `preload()` queues `this.load.image('player', /sprites/back/{playerSpeciesId}.png)` and
`this.load.image('enemy', /sprites/front/{enemySpeciesId}.png)` — a real front/back sprite distinction, not
a flip of one asset — plus the opening cry. Every later species change (new wild enemy, Transform,
evolution, forced switch) loads **on demand** with a per-species texture key (`enemy-{id}`, `back-{id}`,
etc.), checked via `this.textures.exists(key)` first — this doubles as a cache, so a species seen once in a
run doesn't refetch.

**Sprites are plain `Phaser.GameObjects.Image`, not spritesheets** — Gen 1 sprites are static 96×96 stills
(the code comments this explicitly). Scale is computed relative to canvas height, capped at 2.5–3×, so large
species don't overrun the canvas. *(This is period-accurate, not a gap to fix — the real RBY battle sprites
are static too; the only "animation" the original games had was the whole-sprite bounce/slide, which is
exactly what's implemented here via tweens.)*

**Image manipulation already in place** (all tween/tint-based — no shaders, no custom pipeline, no particles
anywhere in the client, confirmed by a repo-wide grep for `Pipeline|shader|RenderTexture|postFX|particle`):

| Effect | Mechanism | Where |
|:--|:--|:--|
| Hit flash | `setTint(0xffffff)` for 80ms, then clear | move animation |
| Evolution flicker | `setTintFill(0xffffff)` solid silhouette, 8 flips @110ms toggling old/new texture | evolution animation |
| Transform pulse | scale +12% and back | Transform animation |
| Entry slide-in | position tween | battle/creature entry |
| Idle bob | ±5px y, yoyo, infinite | idle tween |
| Attack lunge | ±50px x | move animation |
| Damage shake | ±8px x, ×3 | on-hit |
| Faint | +80px y + fade to alpha 0 | faint animation |

**`swapPlayerCreature`** (built for the Stage 3 forced-switch feature): sets the tracked species to the
incoming creature, loads `back-{id}` on demand if uncached, resets the player sprite to alpha 1 off-screen
left, tweens it in (400ms, `Cubic.easeOut`), plays its cry, restarts the idle bob. It's written to mirror
`spawnEnemy` but for a *permanent* creature change (like an evolution) — a later win's `resetPlayerSprite`
reverts to *this* creature, not the one that fainted.

**`resetPlayerSprite`**: at battle end, reverts to the true (pre-Transform) species — a plain texture swap,
no tween.

**Species → texture-key convention**: `player`/`enemy` for the initial pair, `{front|back}-{speciesId}` for
everything loaded afterward. No central lookup table — each call site builds the key inline.
**Fallback/placeholder handling: none.** There is no default/missing-sprite texture, and a failed image load
isn't explicitly handled — it relies on Phaser's own (unhandled-here) loader error event. Worth knowing if
the species roster ever grows past what's actually been imported.

### 1.4 Phaser version and what's available but unused

`package.json` pins **Phaser 3.90.0** — no plugins beyond core Phaser (no Spine, no rex plugins). Everything
in `BattleScene.ts` today uses only the base tween/tint/scale/position API. Available in 3.90 and **not**
currently touched anywhere:

- **`Phaser.FX` post-pipeline** (per-GameObject, built into core since 3.60 — no custom GLSL needed):
  `Glow`, `Shine`, `Shadow`, `Pixelate`, `Vignette`, `Wipe`, `ColorMatrix`, `Blur`/`Bokeh`, `Barrel`, `Light`.
  Applied via `.postFX.add*()` on any `Image`/`Sprite` — this is the cheapest lever available and covers
  most of §4 below.
- **Custom WebGL pipelines** — full shader control, if a built-in FX class isn't enough.
- **`Phaser.GameObjects.Particles.ParticleEmitter`** — impact/type-colour particle bursts.
- **`RenderTexture`** — compositing/snapshotting (e.g. a cleaner evolution-flicker implementation, or a
  shareable results-screen capture).

### 1.5 Texture filtering — unconfirmed, worth auditing first

The research pass did not find an explicit `pixelArt: true` (or equivalent `antialias: false` /
`roundPixels`) setting in the `Phaser.Game` config in `BattleCanvas.tsx`. **Not confirmed as a defect** —
just not confirmed *set* either. If it's unset, Phaser defaults to linear texture filtering, which softens
any blown-up pixel art; these sprites render at 2.5–3× scale, so an unset flag would visibly blur genuine
Gen 1 pixel art at exactly the size players see it. **This is the single highest-value, lowest-cost thing to
check before any FX work below** — every other idea assumes the base sprite is rendering crisp.

### 1.6 Cry/audio — same pattern, already has a fallback

Cries follow the identical import-time/no-DB-field/ID-convention pattern as sprites (§1.1). At runtime,
`BattleScene.ts` loads `cry-{speciesId}` and plays it on arrival; if the OGG is missing, `playCry()` falls
back to `AudioEngine.playCry(id)`, a Web Audio square-oscillator synth. **This is the only fallback that
exists anywhere in the sprite/audio system** — creature sprites themselves have no visual equivalent (§1.3).

**A second correction, same session as §0's:** the same conversation that assumed the sprites were
placeholder art also described cry audio as "the same deferred bucket as sprites, but cheaper," implying a
gap worth filling with "a handful of curated cries." That was wrong for a different reason than the sprite
claim — `CryDownloader.cs` already fetches the full **legacy 8-bit Gen 1 cry** for every imported species
(1–151) at import time, same as sprites, with the fallback synth above already covering the miss case.
`GENERATION_PROFILE.md` §7.6 only defers the *per-generation asset set* question (a future second
generation's cries), not anything about today's Gen 1 set, which is complete. There's no "curated subset"
idea to scope here — noted so it isn't accidentally re-raised as backlog.

## 2. Known gaps / fragility (not blocking, worth knowing)

- **No fallback texture for a failed sprite load.** A 404 or a not-yet-imported species id would currently
  show nothing rather than a placeholder. Low risk today (roster is 1–151, matching what's imported), but
  worth a one-line guard if the roster ever grows past what's been imported ahead of time.
- **Items store `SpriteUrl` in the DB; creatures don't store anything.** Two different patterns for
  fundamentally the same "import-time asset, ID-keyed" problem. Not urgent, but a future touch to either
  shouldn't assume it also covers the other.
- **No shiny/variant concept.** Not a gap against anything currently planned — just naming that the
  front/back pair is the entire variant space today.
- **Texture filter mode unconfirmed** — see §1.5.

## 3. Ideas — presentation work on top of the existing real sprites

**Status: none of this is ratified.** Sketched here so the conversation has somewhere to resume, per
decision 8's own process (sketch → ratify → build → gates) — nothing below should be treated as scoped or
agreed until it's actually discussed. Ordered roughly cost → impact, cheapest/safest first.

### 3.1 Audit texture filtering (do this first, before anything else)
Confirm/set `pixelArt: true` (or `antialias: false`) in the `Phaser.Game` config. If it's currently
defaulting to linear filtering, this single flag is the highest-leverage fix available — it makes every
sprite the game already has look as crisp as it's supposed to, for free, before spending effort on new FX.

### 3.2 A grounding shadow under each creature
Gen 1's battle scenes plant each creature on a flat platform ellipse. A `Phaser.FX.Shadow` (or even just a
drawn ink-tinted ellipse behind each sprite) would ground both creatures on their "platforms" — and should
use the same ink tone as the now-ratified Kanto Sage HUD (`#15130F`, muted/low-alpha), so the canvas and the
DOM chrome read as one consistent world rather than two.

### 3.3 Differentiate critical hits from normal hits
Today every hit gets the same 80ms white tint flash regardless of whether it's a normal hit or a crit — the
player has no *visual* tell beyond the log text. A `Phaser.FX.Shine` sweep (a diagonal light pass across the
sprite) on crits only, layered on top of the existing tint, would give crits their own visual signature
almost for free — no new sprite art, just a different FX call gated on the existing `IsCritical` flag the
engine already reports.

### 3.4 Type-coloured impact particles
Ties directly into the TODO'd move-animation-family work (`TODO.md` → Web UI Polish): once `MoveUsed` carries
`DamageType` (already flagged as the blocker for that item), a small `ParticleEmitter` burst tinted to the
move's type colour — the same `TypeBadge` palette already used for the type badges — on contact would give
each type family a distinct hit signature. Physical-contact moves get a solid puff; projectile/special moves
get a spark trail. This is the item most worth sequencing *with* the animation-family work rather than
separately, since both consume the same wire field.

### 3.5 Status-condition tint, transient not permanent
A `Phaser.FX.ColorMatrix` desaturation pass while a creature is poisoned/paralysed/asleep — subtle, and
explicitly *transient* (clears the moment the status clears), so it never reads as "recolouring" the sprite,
just afflicting it. Good fit for the request to enhance the existing art without changing what species it
depicts. Colour choice should stay disciplined the same way the HUD now does — poison a muted purple-grey,
paralysis a restrained yellow flicker via the existing tint mechanism rather than a new hue.

### 3.6 A real screen-wipe transition in and out of battle
`Phaser.FX.Wipe` is built for exactly the classic Gen 1 battle-entry transition. Could replace/complement the
current alpha-fade on faint, and give battle start its own iconic beat instead of just appearing.

### 3.7 (lower priority, least period-authentic) Depth-of-field focus pull
A `Blur`/`Bokeh` FX on the non-acting creature during the other's move, to draw the eye — tasteful and cheap,
but the least "1996" of the ideas here since Gen 1 never had anything like it. Worth naming as an option, not
a recommendation, since it trades some retro-authenticity for a modern-feeling polish moment. Flagging the
tension explicitly rather than picking a side.

### 3.8 (internal quality, not player-visible) `RenderTexture` for the evolution flicker
The current evolution flicker toggles between two loaded textures via `setTintFill`. A `RenderTexture`
composite could make this smoother, but this is a "nicer implementation of an already-working effect," not a
new player-facing idea — lowest priority of everything above.
